# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Store management web app for 홍콩반점 중앙대점 (a single restaurant): revenue, expenses, staff schedules, payroll, inventory, checklists, investor ledger. The UI and all user-facing text are Korean; the owner talks to Claude in Korean, so reply in Korean.

Business context that affects features: the store's bank account holder (예금주) is 김기억, who appears in the app as "형" (co-investor; `loans/hyung`, `investor:'hyung'` in 투자관리). The user who manages the app is the largest investor. Money moving between the store account and 김기억 is loans, investment or profit sharing, never revenue or an expense. Transfers with the 홍콩반점 상암점 account (bank name '홍콩반점0410 상') are also money 형 takes, so they belong to the same 형 대여금 (`loans/hyung`, memo prefixed "[상암점 계좌]"). The old separate `loans/sangam` ledger is merged into `loans/hyung` once when 지출관리 loads; legacy `nonOp` kind `loan_sangam` is treated as `loan`. '홍콩반점0410중' is the 본사 물류대금 virtual account, so withdrawals to it default to 본사발주 (`hq`) unless a user rule says otherwise.

## Skills and plugins

The owner wants Claude to pick tools for a task on its own, without being told which skill or plugin to use. Before a task where a skill or plugin could help (design work, documents, spreadsheets, reports and the like), search the plugin catalog first. If something fits, show the install card; the owner only clicks it. If the catalog has nothing and a good skill exists elsewhere (e.g. on GitHub, installed with `npx skills add <owner/repo> -a claude-code -y`), ask the owner once before installing it. Install it at project level (`.claude/skills/`), review its files for anything that sends data out or runs unexpected commands, then commit and push it so later sessions keep it (cloud sessions lose global installs). Skip all of this when the task doesn't need it; most changes don't. Installed so far: `hallmark` (`.claude/skills/hallmark`, design for new pages; use on existing screens only when the owner names it), plus the `frontend-design` plugin on the owner's account.

## Commands

```bash
npm run dev       # Vite dev server
npm run build     # production build to dist/ — use this to verify changes
npm run lint      # ESLint over the whole repo
npx eslint <file> # lint only the files you changed
```

There are no tests. Verify with `npm run build` plus `npx eslint` on the touched files. `npm run lint` already reports dozens of pre-existing errors (unused vars, `react-hooks/set-state-in-effect`, missing effect deps); don't treat those as caused by your change and don't mass-fix them unasked.

The app requires a Firebase login, so it can't be meaningfully exercised headless. Say so when a change is untested in the browser.

Vercel project `hongkong` (team `jmgboss1-5587s-projects`) deploys automatically from GitHub:

- any other branch → a preview URL only

## Architecture

- **Stack:** React 19 + Vite, react-router-dom 7, Firebase Auth + Firestore (no backend server apart from one Vercel function, below), recharts for charts, `qrcode` for QR generation. Plain JSX, no TypeScript, no CSS framework — styling is inline `style={{...}}` objects using the 주문전표·장부 palette (light paper look, chosen by the owner after the old dark/yellow UI read as "AI-generated"): `#FAF9F6` page, `#FFFFFF` panels, `#F3F1EC` fields/chips, `#DCD7CE` rules, `#1D1B18` ink text, `#6E6A63` muted text, `#C3261C` the one accent (짬뽕 red, text on it white), status `#2E7D45` green / `#B42318` red / `#2B5C9E` blue / `#6B4FA0` purple / `#B45309` amber. No emoji in the UI (use words: 수정, 삭제, 메뉴), numbers use the body font with `fontVariantNumeric:'tabular-nums'` (no DM Mono), small radii (4–6). Match it.
- **Owner password reset:** `api/set-password.js` (`POST /api/set-password`, body `{uid, password}`) lets the owner set a staff member's login password from 인원관리 (`SetPasswordBox` in each member's detail; login screen also has '비밀번호를 잊으셨나요?' → `sendPasswordResetEmail`). It verifies the caller's ID token, then uses the service account in Vercel env `FIREBASE_SERVICE_ACCOUNT` (the whole JSON key, never in chat or the repo) to sign a Google OAuth token with `jose` (no firebase-admin), reads `users/{caller}` via the Firestore REST API to require `role:'owner'`, refuses owner targets, and calls Identity Toolkit `accounts:update`. Members added by hand have no auth account (USER_NOT_FOUND).
- **Server function:** besides that, the server code is `api/read-receipt.js` (Vercel function, `POST /api/read-receipt`). It verifies the caller's Firebase ID token with `jose`, sends the photo of the 마감 출력물 to Claude Haiku 5.5 (chosen for cost, well under 1원 per photo; `@anthropic-ai/sdk`, structured output via zod) and returns `{kiosk, baemin, coupang, yogiyo, ddangyeo, pos, baeminOrders…ddangyeoOrders, delivery, total, date, notes}`. 매출입력 shows the photo option only in the 마감 tab: "📲 폰으로 마감 출력물 찍어서 채우기 (QR)" opens `PhoneReceiveModal` (exported from `PhotoAttach.jsx`, `hiRes` adds `?hi=1` so `PhoneUpload` compresses to 1600px) and the received photo is read right away; the user still checks and saves. Slip convention: printed 매출요약 총 결제금액 = 배민; handwritten c/y/d = 쿠팡이츠/요기요/땡겨요 (a bare "ㄴ 금액" by 배달 = 쿠팡이츠); handwritten 키/배/포 = 키오스크/배달 합계/포스; top handwritten number = day total. Needs `ANTHROPIC_API_KEY` in Vercel env; `vercel.json` rewrites everything except `/api/`. ESLint uses Node globals for `api/**`.
- **Redesign (live since 2026-10-26):** every page was repainted to the palette above by a mechanical color/emoji/font/radius mapping; layouts are still the old card layouts and get refined page by page. `RevenueInput.jsx`, `Revenue.jsx` ("YYYY년 M월 매출": 채널별 매출 and 한눈에 ledgers, ledger-row input with 오전/미들타임/마감 text tabs, ruled day table), `Expenses.jsx` ("YYYY년 M월 지출": 돈의 흐름 and 지출 구분 ledgers, 고정지출 and 형 대여금 (collapsed by default; `loanFifo` matches 받음/투자전환 to the oldest 빌려줌 first, so it lists which loans are still open, how long, what was repaid when, and each record's running balance; a `type:'reset'` record (0으로 정리, `{date, before}`) sets the balance to 0 as of its date and closes everything open, records up to the latest reset are folded behind '정리 전 기록 N건 보기' but never deleted because the bank import dedupes against them, and deleting the reset record undoes it) as ruled lists; 지출 입력 opens on the 계좌내역 tab and its 직접 입력 tab is just `MissedExpenseInput` (one line: date, category, amount; the dashboard no longer has it); a whole day is edited inline under its row in the ruled day table (수정), 통장 잔액 맞추기 (`BankReconCard`) as a ledger section; small buttons via the module-level `Btn` component, since passing handlers to a render-time helper trips the React Compiler purity lint) and `Dashboard.jsx` ("YYYY년 M월 장부": a 손익 statement and a 통장 statement as dotted-leader ledger lines, then 매출 추이 under a ruled section title; 지출 is split by the 구분 of `expenseCategories/default`) are the reference screens for the new look (ledger rows with dotted receipt leaders, double rules above the header and the total, comma-formatted money inputs, tabs underlined in the accent). Headings must set `fontFamily:'inherit'` because `index.css` gives h1/h2 a system font. `.page-surface` (in `Layout.jsx`) lets a page paint its own background edge to edge; `.main-content` is left-aligned because `index.css` still centers `#root`.
- **Loading speed.** `App.jsx` loads every page with `lazyPage` (React.lazy + Suspense), so the first download is ~260 KB instead of one 1.4 MB bundle; if a chunk fails to load (a POS tab left open across a deploy) it reloads the page once (guarded by `sessionStorage.pageReloadAt`). Pages should fetch their documents with one `Promise.all` instead of awaiting them one by one (근무관리, 내 기록 and 대시보드 were converted).
- **Page language.** `index.html` is `<html lang="ko" translate="no">` with `<meta name="google" content="notranslate">`: with `lang="en"` Android Chrome auto-translated the Korean UI "from English" into nonsense (퇴근했어요 → 냠냠). Keep it.
- **Firebase config** comes from `VITE_FIREBASE_*` vars in `.env` (`src/firebase.js` exports `auth` and `db`).
- **Pages hit Firestore directly.** Each page in `src/pages/` loads with `getDoc`/`getDocs` inside a `load()` function triggered by `useEffect` on the selected month, and saves by rewriting the whole document with `setDoc`. There is no shared data layer, and helpers (`pad`, `mLabel`, `daysIn`, wage/schedule lookups, default expense categories) are duplicated per file. When the same logic lives in several pages (e.g. salary calculation exists in both `Payroll.jsx` and `Dashboard.jsx`), change all copies.
- **Month-keyed documents.** Most data lives in one doc per month, id `YYYY-MM`, with day keys `'01'..'31'` inside: e.g. `expenses/{YYYY-MM}` → `{ '05': { hq, veg, …, deposit }, carryover }`, `revenue/{YYYY-MM}`, `workhours`/`workextra`/`workmemos/{YYYY-MM}` → `{ uid: { dd: value } }`, `payroll`, `bonuses`, `advances`, `severance`, `payrollOwner`, `fixedExpenses/{YYYY-MM}`. Config docs use fixed ids (`expenseCategories/default`, `fixedExpenses/config`, `loans/hyung`, `investment/records`). Because saves overwrite the whole month doc, re-read the doc right before writing when another screen may have changed it. The store account stays logged in on the POS all day, so store-facing pages (`RevenueInput.jsx`, `Cash.jsx`) re-check the date every minute, reload when it changes, re-read before saving, and write only today's day key with `setDoc(..., { merge: true })`.
- **Expenses are written from more than one screen.** Besides `Expenses.jsx` (지출관리, including its 직접 입력 tab `src/components/MissedExpenseInput.jsx`, which adds amounts into the same `expenses/{YYYY-MM}` day entries using the categories from `expenseCategories/default`), `ExpensesInput.jsx` (staff 지출입력) writes today's entry. Changes to the expense data shape or categories must keep them in sync.
- **급여관리 지급 현황** (`Payroll.jsx` `payOf`): 지급한 인건비 = advances actually paid this month (records without `carryFrom`) + the remaining pay of employees marked 지급완료; 아직 줄 인건비 = remaining pay of the others. When advances exceed the pay (remaining < 0), "N월 급여에서 빼기" (`carryOver`) writes the excess into `advances/{next month}` as `{id:'carry-<YYYY-MM>', carryFrom, memo:'N월 초과 가불 이월'}` and stores `carriedOut`/`carriedTo` on `payroll/{YYYY-MM}[uid]`, so this month ends at 0; 되돌리기 (`undoCarry`) or deleting the carried advance next month clears both sides. Both sides are written by module-level `setCarry(uid, month, total)`; carrying again adds to the month's existing `carriedOut`, and `chainCarry` passes any change on through later months that had already carried onward (so carrying September after October updates November). The top of the page is a ledger: 이달 인건비 (세후+상여) = 지급한 돈 + 아직 줄 돈 + 지난달에 미리 준 돈 − 다음 달로 넘긴 가불 − 아직 안 넘긴 초과 가불; 퇴직금 is a separate line. `advances` is read only by Payroll.
- **History-based settings.** Per-employee wage and schedule changes are stored as `wageHistory` / `scheduleHistory` arrays of `{ month, … }` on the `users` doc; the effective value for a month is the latest entry with `month <= curMonth`. The owner's own salary config (`payrollOwner`) follows the same carry-forward rule.
- **Roles and routing.** `src/AuthContext.jsx` loads `users/{uid}` and exposes `isOwner`, `isStore`, `isInvestor`, `isPending`, and `isLegend` (staff with 12+ months tenure, derived from `joinDate`). The owner sets each account's `role` (`staff`/`store`/`investor`) in 인원관리's edit form. Route access is enforced in `PrivateRoute` in `src/App.jsx` (`ownerOnly`, `storeOk`, `storeOnly`, `investorOk`, `legendOnly` flags); a denied route redirects to the role's own home (`homePath`), never to another role's page, and the visible menu per role is defined separately in `src/components/Layout.jsx`. Adding a page means updating both. The PC sidebar is a pictogram rail (72px; icons in `src/components/NavIcon.jsx`, keyed by the menu path, inline SVG line drawings, no emoji), each icon on a tile tinted by its group (`src/lib/nav.js` `navGroupOf`: 돈 blue, 사람 purple, 매장 운영 amber, 대시보드 ink); hovering or focusing shows the name in one fixed-position tooltip so the scrolling menu does not clip it, and '이름 보기' widens it to 208px with labels (per device, `localStorage nav.wide`; 탭 순서 바꾸기 always shows labels). A new page needs an icon in `NavIcon.jsx` (and a group in `nav.js` if not 돈); the mobile bottom tab bar and drawer show the same icons with labels. Each account can reorder its menu ("↕️ 탭 순서 편집"); the order is saved as `menuOrder` (array of paths) on `users/{uid}`, and menus missing from a saved order are appended in default order, so new pages show up without migration. Any Firestore security rules live in the Firebase console, not this repo.
- **NFC 출퇴근.** A sticker at the store entrance holds the URL `/clock`; `App.jsx` renders `Clock.jsx` there without the Layout (and `Login` in place when logged out, so the same URL works after logging in). Opening it checks the phone's position against `attendance/_config` (`{lat,lng,radius}`, saved by the owner from 근무관리 → NFC 출퇴근 → 설정 while standing in the store; without it any location is accepted), then writes `attendance/{YYYY-MM}` → `{uid: {dd: {in, out (serverTimestamp), schedStart, schedEnd, name, …}}}` with `setDoc(..., {merge:true})`: no `in` today → clock in; `in` without `out` → clock out (within 2 minutes of clocking in it asks instead; a tag before 06:00 closes an open record from yesterday; a later tag with yesterday still open leaves it open (no hours counted until the owner enters the clock-out time in AttendancePanel's 퇴근 안 찍음 list), clocks in for today and tells the person to report yesterday's clock-out time). Planned times come from `shiftTimes` (`{weekday: {start,end}}`, set per weekday in 인원관리) and are copied onto the record at clock-in. Since 2026-11 only the start is planned: `end` is optional everywhere (shiftTimes, 근무표 cells, `planFor`; screens that need an end for display math, like Staff's 시간대별 인원, assume 22:00 via `endMinOf`). `calcRecord` counts from the planned start (or earlier with `earlyOk`) up to the actual clock-out with no cap or late approval, except records where the owner had set `lateOk:false` (capped at `schedEnd`); a recorded break is subtracted only if the person was in for the whole break. 조퇴 is no longer detected automatically: the owner ticks 조퇴 in AttendancePanel's edit row (`earlyLeave:true` on the record) and `dayStatus` returns `leftEarly: 1` for it; the owner corrects hours by editing the in/out times there. Arriving more than `GRACE_MIN` (10) minutes before the planned start gives `early` minutes that count only with `earlyOk`, and a day with no planned shift counts only with `unschedOk`. `applyRecord` writes the counted minutes into `workhours` (hours) and `workextra` (minutes) for that day and stores `appliedMins`; the phone tries this on clock-out, and `AttendancePanel` (top of 근무관리) re-applies any record whose computed total differs from `appliedMins` (so hand edits in the table survive), lists approvals, open records without a clock-out (owner fixes times there), and the tag URL. Firestore rules must let staff write their own key in `attendance/{month}` and read `attendance/_config`. `monthStatus` (same file) derives 지각 (clock-in after the planned start, by any minute), 조퇴 (owner-marked `earlyLeave`) and 결근 (a planned day with no clock-in, skipping Sundays, `checklist/holidays`, days the person handed to a confirmed 대타, days before `_config.since` (default 2026-11-01) or the join date, and days the owner marked `excused` in AttendancePanel); a month with work and none of the three is 개근. AttendancePanel lists each person's month, lets the owner mark absences 결근 아님, and has a 연습해 보기 game (not saved). 개근 포상 runs the month after (`src/lib/rewards.js`): `RewardPrompt` (대시보드 and top of 근무관리) asks about last month's 개근 people (`loadEligible`) with three choices: 직원이 각자 룰렛 (`rewards/{YYYY-MM}` = `{status:'open', prizes, eligible}`), 지금 사다리 (`RewardGame`, saves `list`, status 'done') or 안 함 ('skip'); it then lists results and adds unpaid amounts to `bonuses/{YYYY-MM}` (`addRewardBonuses`, marks `paid`). Each eligible staff member spins once from 내 기록 (`MyRewardSpin`, writes only `spins[uid]` after re-reading), and the store account's 체크리스트 shows last month's 개근 names with their prizes. Amounts are parsed from prize text like '2만원' (`parseAmount`). Staff see their own month in 내 기록 via `MyAttendance`. 주휴 keeps a week whose missed 소정근로일 are covered by memos containing '대타'; `withSubMemos` (same file) adds '대타' for days the person handed to a confirmed 대타 on the 대타 게시판, applied to a calculation copy of the memos in Payroll, WorkManage and Dashboard (stored memos are untouched). 브레이크: `_config.breaks` (weekday → {start,end}, default `DEFAULT_BREAKS` = Saturday 14:30~16:30) and `_config.breakDates` (date → {start,end} or {none:true}, for weekdays decided on the day); `breakForShift` attaches the break to a record at clock-in only when the planned shift contains the whole break (full-timers), `calcRecord` subtracts break minutes (`breakMins`) unless `noBreak`, the owner can set a record's break or 못 쉼 in AttendancePanel's edit row (`editedBreak` keeps later date changes off it), and saving a 날짜별 브레이크 rewrites that day's records and re-applies hours. The 스케쥴 근무표 shows 휴게 and the 시간대별 인원 table leaves people out of hours they spend entirely on break. 근무관리's 오늘 근무 view shows each person's NFC times and 지각/조퇴 next to the hour inputs (inputs are keyed by value so NFC-filled hours show after reload).
- **스케쥴** (`Staff.jsx`, `/staff`, staff and owner): 가입 승인 대기 (owner), 지금 매장 (today's people by planned start: 출근 예정 / 근무 중 / 아직 안 옴 N분 지남 / 퇴근, refreshed every minute), a Monday-first weekly 근무표 built from each person's `shiftTimes` with confirmed 대타 swapped (`substitutes/requests`), 임시휴무 and Sundays greyed, past days overlaid with NFC times, 지각/조퇴 and 결근, a 매장 일정 row editable by the owner (`events/{YYYY-MM}[dd]`, also shown in 내 기록), and a 시간대별 인원 heat table counted from the planned shifts. The old monthly calendar of past hours and the duplicate 직원 목록 were removed. 근무표 editing (owner): `schedule/{YYYY-MM}` = `{shifts:{uid:{dd:{start,end}|{off:true}}}, closeAt:{dd:'HH:MM'}}`; `planFor(user, date, plan, uid)` (lib/attendance) is the effective plan everywhere (Clock at clock-in, `monthStatus` for absences, the 근무표): a cell override, else the weekday pattern `shiftTimes` (now only for fixed-schedule staff), then cut at that day's 일찍 마감 time (a shift starting after it disappears). Clicking a cell sets that day's time, 휴무 or 기본으로 (times are picked with `src/components/TimePick.jsx`, hour + 5-minute selects, because iOS `type="time"` inputs overflow table cells and their Reset button cannot clear a value; 인원관리 shiftTimes use it too, with 지우기; AttendancePanel's record edit row uses it with `step={1} allHours` because real clock times need any minute and 00–23h); the 일찍 마감 row sets `closeAt`; 지난주와 같게 copies last week's overrides. Changes to today or earlier call `reapplyDay`, which rewrites that day's records' schedStart/schedEnd (and break unless `editedBreak`) and re-applies hours, so leaving at an early close is not 조퇴. Clock falls back to a confirmed 대타 shift when the person has no plan that day. 인원관리 offers `avgHoursFromPattern` to fill 평균근무시간 (used by 주휴 '소정근로 기준' and 퇴직금) from the weekday pattern.
- **우리 매장** (`OurStore.jsx`, `/our-store`, owner + store account via `storeOk storeOnly`): a top-down pixel-art SVG of the store drawn from the owner's hand-drawn floor plan (`src/lib/storeMap.js`, 960×620): kitchen at the top left (면 and 싱크 on the top wall, an island of 웍 3 · 빈 칸 · 튀김 · 퇴식 over POS · 조리대 · 냉장 · 정수 · 쓰레기, entered through the dashed gap between the 선반 and the island; two 냉장고 below the 선반), 화장실 · 술 · 창고 along the bottom-left wall, 4-person tables 1–6 (5 and 6 right of the kitchen partition, 셀프바 below them), 2-person A1/A2 and 1-seat bar B1–B3 on the right wall, 에어컨, 키오스크 and the 출입문 in the bottom wall. Characters only walk along the walkway graph (`NODES`/`EDGES` in storeMap.js; `route` is a shortest path, `Walker` steps node by node at constant `SPEED`), so they never cross tables or counters; every position slot (`SLOTS`) and `HALL_POINTS` entry is a node name. When moving nodes or furniture, keep edges clear of furniture rects. Customers sit on real seats in `SEAT_ORDER` (today's revenue / 100,000, max 31). Each clocked-in staff member's character works at their `users.positions` (several allowed, set in 인원관리; `position` keeps the first; `POSITIONS` in `src/lib/avatar.js`, default hall) and moves between them every 9–14 s (`pick`: hall means walking between `HALL_POINTS`, other positions are one stable slot each; a 2 s `beat` drives it and `Walker` shows the walk pose while walking; people landing on the same node step aside). The owner (`role: 'owner'`) is always present without clocking in, mostly in the kitchen with occasional hall rounds, labelled 사장님, and edits their own look from an `AvatarEditor` at the bottom of 우리 매장. Rests by the 술 보관함 and 창고 (`r1`/`r2`) during their record's break, walks in from the door for two minutes after clocking in and out to it for one minute after clocking out (saying '퇴근하겠습니다. 수고하셨습니다!' in a speech bubble), then disappears (people who clocked out are not listed). Those one- and two-minute windows are timed by this device's clock from the moment the attendance snapshot first shows the new `in`/`out` (`seen`), not by comparing server timestamps with the local clock, because a POS clock running behind the server kept leavers standing at the door. Badges above heads: 불꽃 = this month's `monthStatus` still 개근, 병아리/별/왕관 = `calcGrade` tenure, 노란 별 = today's checklist complete (checklist records are store-wide, not per person). Delivery bags on the 조리대 = delivery revenue / 120,000. attendance, revenue and checklist records are `onSnapshot` so a POS left on it updates live. Characters: `Avatar.jsx` (16×20 pixel SVG; `apron={false}` for customers), looks from `users.avatar` edited by staff in 내 기록 (`AvatarEditor`), else `defaultLook(uid)`. - **Bank statement import** (`src/components/BankImport.jsx`, the 📑 계좌내역 엑셀 tab in 지출관리) reads bank .xls/.xlsx/.csv exports with SheetJS (`xlsx`, pinned at 0.18.5 because the official SheetJS CDN is unreachable from the dev environment) and KB 국민은행 "계좌 거래내역 조회" PDFs (optionally password-protected) with `pdfjs-dist`; both are lazy-loaded. PDFs from macOS "Save as PDF" put each glyph in its own text item, so lines are rebuilt by x-gaps; the parse is checked against the PDF's 총 출금/입금금액. Columns are found by Korean header names, withdrawals are added to `expenses/{YYYY-MM}` categories. Deposits are reconciled, not added: for every day in the statement period (PDF 조회기간, else min..max date) `deposit` is set to that day's included deposit total, so re-uploads are idempotent and hand-entered 실입금액 is replaced; deposits from the 예금주 are excluded by default and per-sender exclusions are remembered as `__skip_in` rules. Transactions with '홍콩반점0410 상' default to the 형 ledger the same way. Transactions with the 예금주 default to the "형과의 단기 대여금" ledger (`loans/hyung`, withdrawal → `lent`, deposit → `received`) instead of expenses/실입금; ledger entries written by the import carry `bankKey`, and an existing entry with the same date, type and amount is treated as a duplicate. Imported transaction keys are saved in the same write as the amounts, as `importedKeys` on `expenses/{YYYY-MM}`, so a re-upload can't double-count; code iterating an expenses doc must only treat two-digit keys as days. Picking a category changes only that row (other rows with the same 내용 are filled only if still blank), because the same name can mean different purposes (e.g. two people named 이주연). Chosen categories are remembered as keyword rules in `expenseImportRules/default` only when every row of that name got the same choice, which is optional (import still works if that read/write is denied). Users can save only the rows they have categorized; the rest stay on screen. Withdrawals matching a 고정지출 item (same month, same amount, nearest due day) are linked: if that item is already marked paid in `fixedExpenses/{YYYY-MM}` the row is excluded as a duplicate, otherwise saving it also marks the item paid on the withdrawal date. This is a fourth writer of `expenses` docs.
- **Operating vs bank balance.** 영업 잔액 = 전월 이월 + 실입금 − 지출 (what dashboard/지출관리 show); it is *not* the bank balance. Transactions that are neither expense nor revenue (형 대여금, 투자·정산, 개인 이체, 기타) are recorded by the import as `nonOp: [{key,date,dir,amount,kind,desc}]` on `expenses/{YYYY-MM}`, and every statement transaction key is kept in `bankSeen` (keys encode `date|time|out|in|balance|desc|n`, so totals and opening/closing balances can be recomputed and partial uploads merge). `src/lib/bankRecon.js` (`bankSummary`) computes 영업 잔액 + 영업외 입금 − 영업외 출금 vs the real closing balance and splits any difference into: 이월 vs bank opening, unhandled deposits, unhandled withdrawals, and expenses not paid from the account; these always sum to the difference. Shown by `BankReconCard` in 지출관리 and in the dashboard's 영업 잔액 KPI. Under the 통장 밖 지출 reason, '어느 지출인지 찾아보기' opens `OffBankList` (`offBankDetail` in `bankRecon.js`): per day × category, entered amount minus the imported withdrawals whose `bankCls` is that category; rows matched to an 'ack' withdrawal (same amount, ±3 days) are shown as 정상, others flag 두 번 적힘 의심 when a withdrawal of the same amount within 3 days sits elsewhere, and a button subtracts the off-bank amount from that cell (re-reads first). The card lists unhandled withdrawals (in `bankSeen` but in neither `importedKeys` nor `nonOp`) and lets the owner classify them in place: a category adds the amount, a 영업 외 kind adds a `nonOp` entry (and a loan-ledger entry for 형/상암점), and '이미 지출에 있음' only adds the key to `importedKeys` (links an expense entered elsewhere without adding it). The import does the same linking automatically for withdrawals matched to an already-paid 고정지출. Withdrawals can also be classified as 투자관리 회수 (`INVEST_OPTIONS` in `bankRecon.js`, values `__inv:<investor>:<category>` matching Investment.jsx's INVESTORS/CATEGORIES_BY_INVESTOR): they are stored as `nonOp` kind `invest` with `investor`/`category` and appended to `investment/records` with `bankKey` (once per bank transaction) via `appendInvestmentRecords`. Each imported expense withdrawal's category is kept in `bankCls` ({key: categoryId|'ack'}) so it can be moved later: `src/lib/bankReclass.js` (`reclassify`) undoes a transaction's current classification (category amount, `deposit`, `nonOp`, loan-ledger or investment record by `bankKey`) and applies the new one; rows imported before `bankCls` existed get it filled in when 지출관리 loads (`inferLegacyCls`: import rules, then the only day category with enough remaining amount; amounts are untouched), and any still ambiguous ask which category they are in. UI: `BankTxList` inside the reconciliation card (whole month) and, with a `day` prop, under each row of the 지출 내역 table ("▸ 거래 N건") so a day's lump sum can be split back into its individual transactions.
- **투자관리** (`Investment.jsx`): `investment/config` holds per-investor settings plus `additions` (extra money put in later: `{id, month:'YYYY-MM', date?, amount, kind:'investment'|'operating', noInterest, memo}`) and `transfers` (`{id, date, investor, from, to, amount}`: over-recovered money moved to another category of the same investor; category totals = records ± transfers, overall recovered = records only). Each addition is its own recovery category `add:<id>` (`categoriesFor`) with its own target (amount + 5% simple interest from its date or the 1st of its month). `allocateInvest` pours category `investment` recoveries (including bank-import ones) into additions first, oldest first, then the original investment; records with `add:<id>` pay that addition directly. Each piece's interest stops on the day it is fully recovered; money left after every piece is the investment row's excess. `saveConfig` keeps the stored `transfers`; record saves re-read `investment/records` because the bank import also appends to it.
- **매출분석** (`SalesAnalysis.jsx`, `/sales-analysis`, owner + store account only via `storeOk storeOnly`): per delivery app daily orders, sales and 객단가 for a date range (small multiples, one chart per app), plus 할인·이벤트 일정 stored in `revenue/_salesEvents` (`{list:[{id,title,kind,platforms,from,to,memo}]}`; kept in the revenue collection because the store account can write there, so any code that reads the whole revenue collection must skip ids starting with `_`). "효과 보기" compares the event's days (up to today) with the same number of days right before and with the same weekdays of the 4 prior weeks, per app, non-target apps shown as a control. Order counts come from `baeminOrders`/`coupangOrders`/`yogiyoOrders`/`ddangyeoOrders` on the 마감 row of `revenue/{YYYY-MM}[dd]`, entered in 매출입력's 마감 tab (also read from the photo) and removed with the 마감 entry in 매출관리; orders and 객단가 average only days that have a count. Past data comes from the apps' owner-site Excel files via `src/lib/deliveryImport.js` ("📥 배달앱 엑셀로 예전 자료 넣기"; formats found by header names, 쿠팡이츠 매출내역: one row per order, cancels are negative '취소' rows, 가게 부담 할인 = 쿠폰 상점부담 + 즉시할인, payout = 정산금액 산정후; 배민 정산명세서 '상세' sheet: one row per 정산대상일 × 주문유형 with no order-count column; 배민 delivery orders are counted exactly from the per-order 배달비 (`DELIVERY_FEE` 3,400; matches the slip's '배달 N건'), 포장/가게배달 are estimated from that day's average delivery order (`ordersEstimated`); a 마감-entered count beats the Excel count for that day, payAmount = 주문금액 − 파트너부담쿠폰/즉시할인/메뉴할인 (matches the printed 총 결제금액), discount adds the 배달팁 즉시할인, 우리가게클릭 rows become `ads` spread over their date range, payout is null until 입금완료; 땡겨요 부가세신고내역: one row per order with 주문번호/주문일/주문결제/매출할인, ending at a '합 계' row; 요기요 정산내역 '상세 거래내역' sheet: one row per order, the header repeats per store (배달 and 포장 stores) and a totals table follows, so only rows with a 주문번호 count, refunded orders (환불일시) are skipped, discount = the 가게부담 columns, ads = 추천광고이용료, payout = 주문금액 + 컵보증금 − discounts − fees, matching the 요약 sheet's 정산금액). Password-protected files (배민) are decrypted in the browser by `src/lib/officeDecrypt.js` (Office Agile encryption via WebCrypto; the password is asked for and never stored). Saved per month in `revenue/_apps-{YYYY-MM}` as `{[app]: {dd: {orders, sales, orderAmount, payAmount, totalAmount, discount, payout}}, [app]SalesField}`; `sales` is the amount column the user picked (default: the one closest to what 매출입력 has for those days, else 결제금액). Where an app has an Excel day it overrides the 매출입력 values for that day.
- **Carry-over.** `expenses/{YYYY-MM}.carryover` is filled automatically from the month's own statement opening balance (`carryoverSource:'bank'`) or else the previous month's statement closing balance (`'bank-prev'`), both on import and when 지출관리 loads. A value saved by hand is `carryoverSource:'manual'` and is never overwritten (the UI offers "통장 잔액 기준으로 되돌리기").
